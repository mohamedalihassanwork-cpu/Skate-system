## أ. كيف يتنظم المشروع

### هيكل التوثيق

يعتمد المشروع على نظام توثيق منظّم موجود في مجلد `docs/`. كل وثيقة لها غرض محدد:

| الوثيقة | الغرض |
|---|---|
| `docs/PROJECT_STATE.md` | **الحالة الفعلية الآن**: الطور الحالي، المهام النشطة، القرارات المعلقة، الالتزامات |
| `docs/PROJECT_MAP.md` | **خريطة التنقل**: أين يوجد كل ملف أو وحدة في المشروع |
| `docs/00-governance/SOURCE_OF_TRUTH.md` | **مصدر الحقيقة**: ترتيب أولوية المستندات عند التعارض |
| `docs/00-governance/AI_AGENT_RULES.md` | **قواعد الوكيل**: ما يجب أن يفعله ولا يفعله الوكيل |
| `docs/00-governance/DEFINITION_OF_DONE.md` | **تعريف الاكتمال**: متى تعتبر أي مهمة منجزة فعلًا |
| `docs/00-governance/CHANGE_REQUEST_PROCESS.md` | **طلبات التغيير**: كيف تُطلب التغييرات وتُوثَّق |
| `docs/architecture/` | **الهندسة التقنية المستهدفة**: قواعد البيانات، API، الواجهة، الخادم، الأمان |
| `docs/modules/` | **توثيق كل وحدة عمل**: الإيجارات، العملاء، الصيانة... إلخ |
| `docs/phases/` | **خطة كل مرحلة تطوير** (Phases 00–18) |
| `docs/quality/` | **استراتيجية الجودة والاختبار** |
| `docs/decisions/DECISION_LOG.md` | **سجل القرارات**: كل قرار تقني أو تجاري مع سببه وتأثيره |
| `docs/CHANGELOG.md` | **سجل التغييرات المهمة** للمشروع |

### مصدر الحقيقة (أهمية الأولوية)

عند التعارض بين مستندين، يتبع الوكيل هذا الترتيب:

```
1. قرار تجاري معتمد صراحةً من صاحب المشروع  ← الأعلى
2. طلب تغيير معتمد (Change Request)
3. مواصفة المنتج / العمل التجاري الأساسية
4. الهندسة التقنية المعتمدة
5. مرجع التصميم البصري المعتمد
6. مواصفة المرحلة المعتمدة
7. التنفيذ الفعلي الموجود والموثَّق
8. افتراض الوكيل                             ← الأدنى
```

```

     ↓

     ↓

```

2. إذا كان التغيير آمنًا، نفّذه.

## د. كيف تتعامل مع الأخطاء (Bugs)

يجب على الوكيل عند أي خطأ:

1. **إعادة الإنتاج** — يثبت أن الخطأ موجود فعلًا بخطوات واضحة
2. **تحديد السبب الجذري** — لا يُصلح أعراض الخطأ فقط
3. **تقدير الأثر** — ماذا يؤثر هذا الخطأ؟ هل يمس البيانات المالية؟
4. **الإصلاح بحد أدنى** — لا يُعيد كتابة الملفات غير المعنية
5. **اختبار الانحدار** — يتحقق أن الإصلاح لم يكسر شيئًا آخر
6. **تحديث التوثيق** — إن تغيّر سلوك موثّق
7. **Commit + Push**
8. **تقرير**: ما الخطأ، ما سببه، ما الإصلاح، ما اختُبر

### نموذج رسالة: إصلاح خطأ

```
هناك خطأ في [اسم الوحدة]:
[وصف الخطأ بدقة]
[خطوات إعادة الإنتاج إن أمكن]

1. اقرأ توثيق الوحدة ذات الصلة فقط.
2. حدّد السبب الجذري.
3. أصلحه بحد أدنى من التعديلات.
4. تحقق أن الإصلاح لا يكسر شيئًا آخر.
5. كوميت + رفع + تقرير.
```

## و. كيف تتعامل مع تغييرات قواعد العمل

**قاعدة مطلقة: لا تُغيّر قواعد العمل بصمت.**

أي تغيير في قواعد العمل يستلزم:

1. موافقة صريحة منك أولًا
2. تحديث المواصفة أو إضافة طلب تغيير
3. تحديث توثيق الوحدة المعنية
4. إضافة قرار في DECISION_LOG.md
5. تحديث PROJECT_STATE.md إن لزم
6. تحديث التنفيذ والاختبارات
7. توثيق في CHANGELOG.md
8. Git Commit + Push

> [!WARNING]
> إذا اقترح الوكيل تغيير قاعدة عمل دون طلب منك، رفض التغيير واطلب منه توثيق الاقتراح كـ "طلب تغيير معلّق" دون تنفيذه.

## ز. كيف تتعامل مع تغييرات قاعدة البيانات

**قاعدة صارمة: لا تُعدَّل قاعدة البيانات الإنتاجية مباشرةً أبدًا.**

كل تغيير في المخطط (Schema) يتطلب:

1. إنشاء ملف migration (ترقية مخطط)
2. فحص الجداول والعلاقات المرتبطة
3. التحقق من تشغيل الـ migration نظيفًا
4. اختبار استراتيجية التراجع (Rollback) حيثما أمكن
5. تحديث `docs/architecture/DATABASE_ARCHITECTURE.md`
6. لا يُحذف تاريخ العمليات التجارية إلا بموافقة صريحة

### نموذج رسالة: تغيير في قاعدة البيانات

```
أريد إضافة [عمود/جدول] إلى قاعدة البيانات.

1. حلّل الأثر على الجداول الحالية.
2. أنشئ ملف migration مناسب.
3. تأكد من أن الـ migration يعمل والـ rollback ممكن.
4. حدّث DATABASE_ARCHITECTURE.md.
5. لا تُعدّل بيانات الإنتاج الموجودة.
```

## ح. كيف تتحقق من مرحلة تطوير

عند اكتمال أي مرحلة، اطلب من الوكيل:

| نوع التحقق | ما يجب التحقق منه |
|---|---|
| **التحقق من التنفيذ** | هل الكود يعمل؟ |
| **التحقق الوظيفي** | هل قواعد العمل محترمة؟ |
| **التحقق من الانحدار** | هل كسر أي شيء كان يعمل؟ |
| **التحقق من RTL والواجهة** | هل العربية والاتجاه RTL صحيحان؟ |
| **التحقق من الأمان** | هل الصلاحيات محمية من جانب الخادم؟ |
| **التحقق من التوثيق** | هل وُثِّق كل شيء؟ |
| **التحقق من Git** | هل الكوميت صحيح والرفع تم؟ |

### نموذج رسالة: التحقق من مرحلة

```
تحقق من اكتمال المرحلة [XX]:
1. ما الملفات التي تغيرت؟
2. ما الاختبارات التي نُفِّذت وما نتائجها؟
3. ما قواعد العمل التي تم التحقق منها؟
4. هل RTL واللغة العربية تعمل بشكل صحيح؟
5. هل الصلاحيات محمية من جانب الخادم؟
6. هل التوثيق محدَّث؟
7. ما هاش الكوميت؟ وهل تم الرفع؟
8. ما الذي لا يزال معلقًا؟
```

## ي. كيف تتعامل مع ادعاءات الوكيل

**لا تقبل كلمة "تم" أو "Done" وحدها كدليل.**

الوكيل يجب أن يُقدّم في تقرير الإنجاز:

| العنصر | الوصف |
|---|---|
| ما الذي تغيّر | قائمة الملفات المُعدَّلة |
| أين تغيّر | المسارات الدقيقة للملفات |
| ما الذي اختُبر | الاختبارات التي نُفِّذت ونتائجها |
| ما الذي تم التحقق منه | قائمة التحقق |
| ما الذي لا يزال معلقًا | أي مهام مؤجلة أو غير مكتملة |
| هل التوثيق محدَّث | نعم/لا مع تفصيل |
| هاش الكوميت | مثال: `36a2c48` |
| حالة الرفع | تم الرفع / لم يُرفع |
| القيود المعروفة | أي شيء لا يعمل بشكل مثالي |
